# Goal

Deliver a read-only, source-bound Knowledge Visor V1 that makes a project's
ledgers, journals, events, and verification record useful to a decision maker
without treating the knowledge base as a task database or inventing claims.

# Task Contract

- Intended outcome: Replace the current narrative-first visor with a calm,
  scientific white-paper interface containing Workspace, Activity, and Evidence
  tabs; one accessible, read-only detail layer; deterministic observation
  validation; and a linked white-paper artifact.
- Observable success criteria: A fixture report provides the three tabs, a
  light/dark theme switch, topic/grouped journal access, filtered activity,
  source-linked observations, evidence/provenance, and HTML/PDF white-paper
  artifacts whose manifests bind them to the same snapshot and observations.
- Constraints and non-goals: Preserve the optional/dormant launcher, local
  self-contained report, no browser network, no WebSocket/polling, no editing,
  no productivity scoring, and schema-3 OKF compatibility. Canonical records
  remain Markdown/YAML; reports are derived artifacts.
- Open questions and assumptions: Existing records do not yet have an explicit
  persistent decision-relationship schema. V1 may display only relationships
  present in sources and must label the rest as unknown rather than infer an
  override from prose.

# Execution Boundaries

- Authorized scope and exclusions: Modify the optional dashboard renderer,
  viewer, tests, documentation, component/release manifests, and the active
  tenant knowledge record. Do not modify a user's canonical project sources or
  add a canonical graph/task database.
- Affected interfaces, owners, and relevant side effects: `dashboard generate`,
  `collect`, `observe`, `render`, and `export` retain their existing entry
  points while producing an expanded report artifact. The release manifest and
  component checksums must change because installed payload bytes change.
- Escalate before changing requirements, external behavior, authority, ownership, dependencies, or acceptance criteria: Stop if producing a deterministic PDF
  requires a new runtime dependency or a new persistent knowledge schema.
- Delegation integrator and remaining integration checks, when applicable: No
  delegation. The current agent owns integration and full report proof.

# Handoff Topology

- Selection: milestone chain. Data trust, presentation, and export are
  independently testable contracts that must compose in order.
- Parent integrator and final end-to-end acceptance: The current agent accepts
  each stage and proves a generated fixture report, source embedding, artifact
  binding, offline boundary, and release certification.
- Milestones:
  1. Normalize journals/events and derive explicit evidence relationships;
     exclude new canonical schema. Proof: deterministic fixture assertions.
  2. Add four source-linked narrative lenses and citation/coverage validation;
     exclude unsourced decision or collaboration claims. Proof: valid and
     deliberately invalid observations.
  3. Render the three-tab, two-layer reader with accessible modal behavior and
     theme persistence; exclude all source edits. Proof: DOM markers and
     browser-independent interaction helpers.
  4. Create snapshot-bound white-paper HTML/PDF artifacts and manifest; exclude
     external rendering services. Proof: artifact files, checksum binding, and
     PDF signature/page validation.
  5. Refresh release integration and compose the complete dashboard boundary
     suite. Roll back by retaining the previous optional report behavior if a
     stage violates local/offline boundaries.

# Existing Approaches

- Relevant project patterns or established approaches considered: The existing
  `collect → observe → render` source-hash boundary, separate presentation
  model, fixture-driven report tests, and isolated report retention already
  solve the trust and lifecycle constraints. The sibling ad-generation
  dashboard supplies the three-view information architecture reference only.
- Why the selected approach fits, or why a novel approach is necessary: Extend
  the existing deterministic pipeline and replace the client view. A compact
  structured white-paper renderer shares the report view model so artifacts do
  not require a remote service or a browser-time request.

# Decisions

- Keep `snapshot.json`, `observations.json`, and `presentation.json` as
  separately inspectable stages and bind every derived artifact to their hashes.
- Use a small cobalt-to-indigo accent only for active/contextual elements; the
  default surface is paper/ink, and dark mode is an explicit reader preference.
- Keep two layers: the main tab surface plus one reusable read-only modal.
- Treat the existing `delivery_estimate` as optional, secondary evidence rather
  than a dashboard centerpiece.
- Use a dependency-free PDF writer for the local companion artifact. The
  printable HTML and PDF share the same prepared report model, avoiding a
  browser engine, external service, or new optional runtime dependency.
