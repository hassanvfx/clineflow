Assess the current ClineFlow rules for solid modular development and
multi-journal handoffs, and define the narrowest guidance-level enhancement
needed to make planning choose a safe handoff topology.

# Work Log

## 2026-09-06 20:35 UTC - Rule review completed

Recovered the current knowledge contract and inspected managed procedures,
Codex guidance, durable methodology, the generated journal starter, tenant
stream behavior, and the preceding workflow-values journal. The workflow
already requires explicit slice boundaries, a delegated-slice integrator,
integration checks, and durable handoff context. Tenant streams prevent
concurrent journal collisions, but they do not model parent/child work or
define whether a plan should use one handoff or multiple milestones.

The recommended enhancement is to make planning choose a handoff topology:
use one handoff only when the work is one independently verifiable slice with
one integration boundary; use a milestone chain when components have distinct
contracts, can be tested in isolation, or must be composed in a defined order.
Every milestone should name its boundary, inputs and outputs, proof, consumer,
and escalation condition. The parent integrator accepts each milestone only
after its local proof passes, then owns the composed integration proof and
final durable handoff.

## 2026-09-06 20:37 UTC - Implementation plan prepared

Plan a guidance-first release with no persistent parent/child journal schema.
Use linked independent streams for milestones and a named integrator as their
coordination point. The work proceeds as follows:

1. Define the normative planning rule in managed procedures. Every substantial
   plan must choose `single handoff` or `milestone chain` before execution.
   A single handoff is allowed only for one cohesive slice with one owner,
   contract, and independently verifiable integration boundary. A milestone
   chain is required when two or more slices have distinct contracts,
   consumers, proofs, ordering dependencies, or composition risk. Do not split
   merely by file count, task size, or number of agents.
2. Define the milestone contract. Each milestone records its owned and excluded
   boundary, entry condition, inputs and outputs, local acceptance proof,
   downstream consumer, dependencies, responsible contributor, integrator, and
   escalation or rollback condition. Milestones cannot overlap ownership or
   claim final end-to-end completion.
3. Define the execution gates. Contributors implement and prove their own
   milestone, publish a durable handoff linked to its stream, and do not merge
   assumptions into the next boundary. The integrator verifies stated inputs
   and local evidence, composes milestones in dependency order, records
   integration results and gaps, and alone closes the parent-level final
   handoff after end-to-end proof.
4. Put this contract in the canonical payload: `template/.clineflow/PROCEDURES.md`
   receives the decision rule, execution gates, and a concrete multi-milestone
   example; `template/configs/rules.template.md` receives the concise agent
   obligation; and both `template/.clineflow/WORKING_WITH_CODEX.md` and
   `template/.clineflow/WORKING_WITH_CLINE.md` receive provider-facing planning
   guidance. Align the source repository's `AGENTS.md`, `.clinerules`, and
   `docs/durable-development-methodology.md` with those operational rules.
5. Make the behavior actionable in every new stream. Extend the journal
   generator in `template/.clineflow/lib/knowledge.py` and both task-template
   copies (`knowledge/journals/TASK_TEMPLATE.md` and
   `template/knowledge/journals/TASK_TEMPLATE.md`) with a `Handoff Topology`
   section. It prompts for the selection rationale, parent integrator, and a
   compact milestone table or list using the contract from step 2. Update the
   legacy-template notice only if its summary needs to name this new prompt.
6. Add focused tests: generated journals contain the topology section and its
   required prompts; fresh installation and historical updates distribute the
   canonical language while preserving user-authored content; release-contract
   tests reject a missing canonical topology rule. Keep behavioral validation
   at document/template level—do not pretend the tooling can decide whether a
   real architectural boundary is sound.
7. Ship it as a managed payload patch: bump the release patch version, refresh
   the release manifest hashes using the project’s supported release workflow,
   and explicitly record that migration schema 2 remains unchanged. Run focused
   suites, then full lifecycle certification, OKF and knowledge-sync validation,
   and whitespace checks. Publish the completed journal and immutable update

# Decisions

- Preserve tenant-scoped journals as the concurrency mechanism; add no
  implication that one journal is automatically a module or milestone.
- Treat the number of handoffs as an intentional planning choice based on
  independently testable boundaries and composition risk, not task size or
  agent count alone.
- Keep final end-to-end proof with one accountable integrator even when child
  milestones are verified independently.
- Keep milestone relationships as human-readable links and prompts in this
  release. Add machine-readable parent/child dependency fields only after real
  users need graph queries, scheduling, or automatic gate enforcement.
