# Goal

Implement the approved design for an opt-in ClineFlow MCP orchestrator. The
system centralizes MCP orchestration and dashboard runtime concerns while
preserving ClineFlow's project-local, Git-oriented knowledge workflow. Fresh
ClineFlow installation will stage the core workflow without a project-local
dashboard runtime, then provision and activate the global MCP layer that owns
dashboard generation once the release artifact gate is available.
The explicit project root is read-only dashboard input (ClineFlow knowledge and
Git facts) and the parent of the sole MCP-owned project workspace.

# Task Contract

- Intended outcome: an opt-in, user-global stdio MCP server developed in
  `mcp-server/` that operates on an explicitly supplied project root and
  automatically registers its credential-free global entry for detected MCP
  clients during installation.
- Observable success criteria: the future implementation exposes the agreed
  consultation resources and lifecycle, health, repair, and dashboard tools;
  it preserves current transactional lifecycle and knowledge ownership rules.
  A first-time user installs ClineFlow and its absent global MCP server through
  one command, understands the server/client outcome, and is left with either
  an active validated connection or explicit client-specific next steps.
- Constraints and non-goals: the server remains opt-in, local, stdio-only,
  credential-free, and project roots are never inferred. The packaged release
  declares its checksum-addressable wheel contract; publication of that wheel
  is a release operation outside this local implementation. Existing update
  and removal behavior remains transactional. Any dashboard-removing update
  must activate MCP before committing project migration.
- Open questions and assumptions: use the official MCP stdio model; package a
  declared compatibility matrix; fetch authoritative contract metadata only on
  explicit latest consultation or upgrade checks; report bundled or cached
  metadata honestly when offline.

# Hardening Requirements

- Explicit global server installation authorizes automatic configuration only
  for detected clients with recognized writable targets; it never creates a
  configuration for an absent client.
- A versioned client registry specifies supported OS paths, parser/format,
  official-CLI route, reload requirement, and exact removal strategy. Unknown
  paths are never discovered through broad filesystem scans.
- Every setup result is serializable per target: client, path, format, action,
  reason, ownership status, and validation result. Actions are `add`, `update`,
  `unchanged`, `skip`, `not_detected`, and `failed`.
- Ownership is exact: entry name `clineflow`, verified absolute stable launcher,
  expected stdio arguments, and no secret or project-root environment. Any
  collision or deviation is `user_managed` and is preserved.
- Each client write uses a same-directory temporary file, validation, and atomic
  replacement. Cross-client setup is not transactional: validated prior writes
  remain, and a partial outcome returns retry guidance.
- Client entries point only to a stable global launcher. Package updates replace
  the validated release behind that launcher without client-config churn.
- Every repository operation requires an absolute, existing, regular,
  non-symlink root. A target-local operation lock prevents concurrent writes;
  the server never adopts its launch working directory as a target.
- Latest metadata reports `fresh`, `cached`, or `offline` provenance. Unverified
  or incompatible pairs are consultation-only and cannot mutate a project.
- Repair has a finite action vocabulary. Apply rechecks health, backs up only
  affected target data, and refuses ambiguous ownership or malformed sources.
- ClineFlow removal preserves the MCP-owned `.clineflow-mcp/` workspace and
  its ignore marker, plus legacy `knowledge/dashboard/` reports. Global MCP
  uninstall separately previews/removes only exact owned client entries and
  server files; it never removes project workspaces.
- The first MCP release preserves the existing ClineFlow lifecycle contract and
  project ownership behavior. The fresh installer gains a controlled MCP
  activation phase, while MCP code remains distributed and versioned separately
  under `mcp-server/`.
- The global bootstrap acquires an installer lock and classifies its state as
  `absent`, `healthy`, `outdated`, or `corrupt`. It installs only when absent;
  a healthy existing install is reused, an outdated one receives an explicit
  update recommendation, and a corrupt one requires an explicit repair path.
  It never overwrites an existing server implicitly.
- Dashboard readiness is a composite-install gate. The coordinator may stage
  ClineFlow files first, but it must not commit a project state without the
  relocated dashboard unless the global MCP launcher is healthy and client
  setup reaches `active`, `unchanged`, or explicit `not_detected`. Dashboard
  execution may create only the target's `.clineflow-mcp/` workspace; it must
  not recreate a project-local dashboard runtime or write canonical knowledge.

# First-Install Experience Contract

- The standalone global bootstrap is one copyable command. It accepts
  `--dry-run`, `--status`, `--update`, and `--repair`; client setup is an
  explicit part of a successful installation. Composite ClineFlow installation
  always requests detected-client setup because dashboard availability is a
  completion gate.
- The initial state check is shown before download: `absent` proceeds to a new
  install, `healthy` skips package installation and performs only idempotent
  setup reconciliation, while `outdated` and `corrupt` stop with explicit
  update or repair commands. Concurrent bootstrap attempts wait or fail with a
  clear lock result; neither overwrites the other.
- Before writing, preflight prints the platform, resolved stable launcher path,
  server release, prerequisite status, and a per-client configuration plan.
  It explicitly states that no project files, project roots, credentials, or
  secrets will be read or written.
- Installation order is fixed: stage and verify the ClineFlow core; verify or
  install the global server; health-check the stable launcher; calculate client
  plans; atomically apply and validate each permitted client configuration;
  commit the staged ClineFlow core; print restart/reload and verification
  guidance.
- If package install or server health validation fails, no client configuration
  is changed and the staged ClineFlow core is rolled back. A no-client
  environment returns `installed_mcp_ready_no_client_detected` with manual
  setup guidance. A failed selected client is an installation failure, not a
  silent dashboard deactivation.
- The first successful run ends with one verification action per configured
  client and a generic fallback: restart/reload the client, then call
  `clineflow_consult` against an explicit project root. A matching entry on a
  repeat run is `unchanged`; the installer never duplicates it.
- A dashboard-removing ClineFlow update uses the same composite readiness gate.
  Its preflight names the global server/client changes in addition to the
  ordinary ClineFlow migration plan; failure before readiness restores the
  target project to its exact pre-update state.
- Missing prerequisites yield an OS-specific plan and an explicit install or
  retry path. The bootstrap must not silently install unrelated system tools.

# Decisions

- The server is an opt-in, user-global stdio executable; it is not a daemon,
  holds no target-project work, and automatically configures only detected
  supported MCP clients as part of explicit server installation.
- The global installer resolves and writes the installed server's absolute
  executable path, avoiding editor PATH assumptions. It creates a plan first,
  applies only recognized writable configurations, validates each result, and
  reports skipped targets.
- Supported automatic registrations are Codex, Claude Code, Copilot, Cline,
  Cursor, Windsurf, and Continue. Each entry has the stable name `clineflow`,
  contains no project root or secret, and lets the agent provide `root` to each
  MCP tool call.
- Existing unrelated configuration is preserved. Malformed configuration and a
  changed `clineflow` entry are never overwritten; the setup result explains
  the required manual action. Where an official client CLI is available, use
  it and verify the registration instead of directly editing its configuration.
- Automatic registration is authorized by explicit fresh ClineFlow installation
  or direct global-server installation, not ordinary lifecycle calls. It applies
  only to detected recognized configurations and never creates a new config for
  an absent client.
- Client setup consists of independently atomic writes, not one cross-client
  transaction. Validated global entries remain after a client failure, but a
  composite ClineFlow installation or dashboard-removing update rolls back its
  project transaction and reports the retry path.
- Every owned client entry records a stable global launcher, not a versioned
  executable. The parent integrator accepts each handoff stage before release
  composition and owns final cross-platform proof.
- A smooth installation means transparent ordering, not silent side effects:
  one command, a printed preflight, staged ClineFlow core, verified active MCP,
  idempotent repeat runs, and a rolled-back project transaction with exact
  retry guidance when dashboard activation cannot complete.
- The dashboard is relocated into the MCP package. Fresh ClineFlow payloads do
  not contain its project-local launcher, optional runtime, or assets; update
  migration removes verified legacy dashboard state only after MCP readiness.
- Global bootstrap installation is create-only by default: absent installs,
  healthy reuses, outdated recommends explicit update, and corrupt recommends
  explicit repair. No existing MCP package is overwritten during installation.
- `clineflow-mcp setup --status` is read-only; `setup --apply --yes` performs
  idempotent global registration; `clineflow-mcp uninstall` previews exact
  owned client entries and removes them only after explicit confirmation. This
  is distinct from `clineflow_remove`, which only removes ClineFlow from a
  supplied target project.
- Each operation accepts an explicit root. The MCP reads ClineFlow knowledge
  and Git facts there, while every MCP/dashboard write belongs in
  `.clineflow-mcp/`. That sole workspace is ignored through a marker-delimited
  local Git exclude block. New dashboard reports, facts, observations,
  settings, retention records, exports, and operation logs never enter
  `knowledge/`.
- The workspace contract is `.clineflow-mcp/dashboard/runs/<run-id>/` for
  rendered reports and their derived data, `.clineflow-mcp/dashboard/` for
  managed settings and retention state, `.clineflow-mcp/exports/<export-id>/`
  for authorized sanitized exports, and `.clineflow-mcp/operations/<id>/` for
  lifecycle evidence. The server package contains the renderer and static
  assets; no dashboard executable or asset bundle is installed in `.clineflow/`.
- Read-only resources provide the latest contract, OKF schema, and endpoint
  catalog. `clineflow_consult` reports a target's state and compatibility.
- The intended tools are `clineflow_install`, `clineflow_update`,
  `clineflow_remove`, `clineflow_healthcheck`, `clineflow_fix`,
  `clineflow_dashboard_generate`, `clineflow_dashboard_settings`, and
  `clineflow_dashboard_export`.
- Lifecycle authorization mirrors the existing agent/CLI contract. Removal
  always produces a dry-run preview before explicit final-removal authorization;
  the MCP layer adds no server-issued confirmation-token protocol.
- The compatibility matrix gates mutation. Unsupported pairs return a
  synchronized MCP-server then ClineFlow upgrade recommendation.
- Safe repair may restore managed or reconstructible state only. It reports,
  preserves, and backs up ambiguous or malformed user knowledge instead of
  rewriting it.
- The MCP dashboard is the supported dashboard. Fresh install has no
  project-local dashboard runtime; schema-3 update migration removes verified
  legacy dashboard state only after global MCP and client readiness are proven.
  Its packaged renderer writes only the target `.clineflow-mcp/` workspace;
  legacy `knowledge/dashboard/` reports are preserved but never extended.
- The first implementation milestone uses the MCP Python SDK and the existing
  `uv tool` global-install pattern. It has no project-root launch argument:
  every tool receives the root explicitly.
